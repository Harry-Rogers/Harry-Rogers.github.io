<task type="checkpoint:human-action" gate="blocking">
  <name>Task 1: Owner opens a Codespace, runs jekyll serve, and confirms the forwarded port renders</name>
  <what-built>
    The academicpages `.devcontainer/` (shipped unchanged in plan 01) defines a containerised dev environment with Ruby and the github-pages gem preinstalled. This task verifies the entire chain (devcontainer build → bundle install → jekyll serve → forwarded port → rendered HTML) works in a real Codespace.
  </what-built>
  <how-to-verify>
    Owner action (no CLI alternative — must be run inside a real Codespace VM):

    1. Open `https://github.com/Harry-Rogers/Harry-Rogers.github.io` in a browser.
    2. Click **Code → Codespaces → Create codespace on main**. Wait for the container to build (first build can take 2-5 minutes; the devcontainer pulls Ruby + runs the postCreateCommand).
    3. Once the in-browser VS Code is ready, open a terminal (Terminal → New Terminal) and run:
       - `ruby --version` — must print `ruby 3.3.4` (matches `.ruby-version`)
       - `bundle --version` — must print a Bundler version
       - `bundle install` — must complete with no resolver errors. If the devcontainer's postCreateCommand already ran `bundle install`, this is a no-op confirmation.
       - `bundle exec jekyll serve --host 0.0.0.0` — must start the Jekyll server. Expected output ends with: `Server address: http://0.0.0.0:4000` and `Server running... press ctrl-c to stop.`
    4. VS Code should auto-detect port 4000 and surface a notification "Your application running on port 4000 is available." Click **Open in Browser**. The forwarded URL renders the academicpages homepage with no Liquid `{% raw %}` errors visible on screen and no Sass compile errors in the terminal.
    5. In the terminal, scan for errors:
       - `^C` to stop the server, then re-run `bundle exec jekyll build --trace 2>&1 | tee /tmp/build.log`.
       - `grep -iE 'error|liquid exception|sass.*error' /tmp/build.log` — expect zero matches (warnings are OK).

    Record result:
    - **PASS**: All steps complete, no errors. Type "codespaces UAT pass" in the resume signal.
    - **FAIL**: Identify failure mode (devcontainer build error / `bundle install` resolver conflict / Jekyll Liquid error / Sass error / port-forward not working) and paste the relevant error log into the resume signal — that diagnostic then drives a gap-closure plan.

    Note: this is the only `autonomous: false` task in this plan. There is no CLI-only path that exercises the Codespaces VM lifecycle. `gh codespace create` does exist but does not equivalently verify the in-VM `bundle exec jekyll serve` + browser-forwarded port — the visual confirmation in step 4 is the actual UAT.
  </how-to-verify>
  <resume-signal>Type "codespaces UAT pass" if all checks succeed, or "codespaces UAT fail: [diagnostic]" with the error log.</resume-signal>
</task>
