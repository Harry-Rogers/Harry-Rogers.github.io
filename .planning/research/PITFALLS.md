# Pitfalls Research

**Domain:** academicpages (Jekyll/Minimal Mistakes) fork deployed to GitHub Pages
**Researched:** 2026-05-17
**Confidence:** HIGH (well-documented Jekyll/GH Pages mechanics; community pitfalls observed across hundreds of academicpages forks on GitHub Issues)

Roadmap phases referenced below:
- **Skeleton** — fork, rename, get a default site live at the canonical URL
- **Content** — replace placeholder copy, populate `_publications`, talks, teaching, projects
- **Customisation** — dark-mode-only theme, personalisation, Sass overrides
- **Polish** — SEO, OG tags, favicon, link checks, accessibility, mobile

## Critical Pitfalls

### Pitfall 1: Repo name does not match `<username>.github.io` exactly

**What goes wrong:**
Repo named `harry-rogers.github.io` (correct), `HarryRogers.github.io` (works — case-insensitive at the URL), `Harry-Rogers.Github.io` (works), `harry-rogers-github-io` (does NOT deploy as a user site — becomes a project page at `/harry-rogers-github-io/` instead, breaking every absolute path). Common variant: repo accidentally created as `academicpages.github.io` (kept the fork name) and silently serves at `https://harry-rogers.github.io/academicpages.github.io/`.

**Why it happens:**
GitHub Pages has two deploy modes: **user site** (one per account, repo must equal `<username>.github.io`, deploys at root) and **project page** (any repo, deploys at `/<repo>/`). Forks inherit the upstream repo name. The GitHub username `Harry-Rogers` is case-insensitive in URLs but the repo name string is what's matched.

**How to avoid:**
- After forking, immediately go to repo Settings → rename to `Harry-Rogers.github.io` (matches the GitHub username casing exactly — easiest to reason about).
- Verify the canonical URL resolves: `curl -I https://harry-rogers.github.io/` should return `200` (or `301` to HTTPS) within ~1–2 minutes of the rename and first push to `main`.
- Settings → Pages should show: "Your site is live at https://harry-rogers.github.io/" with NO trailing path.

**Warning signs:**
- Settings → Pages shows a URL containing `/academicpages.github.io/` or `/Harry-Rogers.github.io/` (path component present = project page mode).
- Site loads HTML but every CSS/JS/image returns 404.
- Browser dev tools show requests to `/assets/css/main.css` returning 404 when the actual file lives at `/academicpages.github.io/assets/css/main.css`.

**Phase to address:** Skeleton (the very first step — gating)

### Pitfall 2: `_config.yml` `url` and `baseurl` left at academicpages defaults

**What goes wrong:**
Forked `_config.yml` ships with `url: "https://academicpages.github.io"` and (sometimes) `baseurl: ""` or `baseurl: "/academicpages.github.io"`. If `baseurl` is non-empty on a user site, every internal link generated by `{{ site.baseurl }}/foo` becomes `/academicpages.github.io/foo` → 404. If `url` is wrong, `sitemap.xml`, `feed.xml`, OG tags, and canonical `<link>` tags all point at the wrong domain — breaks SEO and absolute share links.

**Why it happens:**
The upstream template is also a user site at `academicpages.github.io`, so its defaults are *almost* correct but not quite. Forkers often only change `title` and `author` and miss the URL keys.

**How to avoid:**
Edit `_config.yml` in the very first commit after fork:
```yaml
url: "https://harry-rogers.github.io"
baseurl: ""          # user site at root — MUST be empty string, not "/"
repository: "Harry-Rogers/Harry-Rogers.github.io"
```
Then `bundle exec jekyll serve` locally and check that links rendered in `_site/index.html` start with `/` (not `/academicpages.github.io/`).

**Warning signs:**
- Nav links 404 in production but work locally (you forgot `baseurl: ""`).
- View-source on the deployed homepage shows `<link rel="canonical" href="https://academicpages.github.io/...">`.
- `https://harry-rogers.github.io/sitemap.xml` lists `academicpages.github.io` URLs.

**Phase to address:** Skeleton

### Pitfall 3: Default branch / Pages source branch mismatch (`master` vs `main`)

**What goes wrong:**
academicpages was authored when GitHub's default branch was `master`. New forks default to `main`. Pages is by default configured to build from `master` on the upstream — after fork, Settings → Pages may show "Branch: master" with a yellow warning ("No such branch") and no deploy ever runs. Symptom: pushes succeed, no build kicks off, site is empty or stale.

**Why it happens:**
Fork inherits Pages settings; rename of default branch doesn't auto-update Pages source.

**How to avoid:**
Settings → Pages → **Build and deployment** → Source: "Deploy from a branch" → Branch: `main` / `/ (root)`. Save. Confirm Actions tab shows a `pages build and deployment` workflow run within seconds of the save.

**Warning signs:**
- Settings → Pages shows "Your GitHub Pages site is currently being built from the master branch" but no `master` exists.
- Actions tab is empty after pushing commits.
- `https://harry-rogers.github.io/` returns 404 with the GitHub Pages 404 page (not your own `404.html`).

**Phase to address:** Skeleton

### Pitfall 4: Relying on Jekyll plugins that are NOT on the GitHub Pages allowlist

**What goes wrong:**
academicpages out of the box uses several plugins; some are allowlisted by GitHub Pages, some are not. Plugins NOT supported by the default Pages builder include: **jekyll-scholar** (BibTeX → HTML rendering), **jekyll-archives** (category/tag archive auto-generation), any plugin in `_plugins/`, custom Ruby in `_plugins/*.rb`. If you add `gem "jekyll-scholar"` to the Gemfile and reference it in `_config.yml` plugins list, the Pages build will fail silently (build error visible only in the repo's "Environments" → `github-pages` deployment log).

The full allowlist (as of 2025): `jekyll-coffeescript`, `jekyll-default-layout`, `jekyll-gist`, `jekyll-github-metadata`, `jekyll-optional-front-matter`, `jekyll-paginate`, `jekyll-readme-index`, `jekyll-titles-from-headings`, `jekyll-relative-links`, `jemoji`, `jekyll-mentions`, `jekyll-redirect-from`, `jekyll-seo-tag`, `jekyll-sitemap`, `jekyll-feed`, `jekyll-include-cache`, `jekyll-remote-theme`, `jekyll-avatar`.

academicpages already uses `jekyll-feed`, `jekyll-sitemap`, `jekyll-paginate`, `jekyll-redirect-from`, `jekyll-include-cache`, `jemoji`, `jekyll-gist` — these are all fine.

**Why it happens:**
Academics search "render BibTeX in Jekyll" → top result is jekyll-scholar → assume it works on Pages. It does not (on the default builder).

**How to avoid:**
Two options:
1. **Stay on default Pages builder (recommended for low maintenance):** Render publications from `_publications/*.md` front-matter — academicpages already does this. Embed BibTeX as a fenced code block inside the publication's Markdown. No plugin needed.
2. **Switch to GitHub Actions build** (`actions/jekyll-build-pages` or a custom `jekyll build` workflow) only if a non-allowlisted plugin is genuinely required. This is what `actions/deploy-pages` enables. Adds maintenance surface — avoid unless needed.

For Harry's scope (8 publications, manual entry is fine), Option 1 is correct.

**Warning signs:**
- Build status in Settings → Pages shows red X with "Page build failure".
- Email from GitHub: "Page build failed" with `unknown tag {% bibliography %}` or `Liquid Exception: Liquid syntax error`.
- Publications page renders the literal `{% bibliography %}` tag as text.

**Phase to address:** Skeleton (decision) + Content (when adding publications)

### Pitfall 5: Ruby / Bundler version drift between local and Pages

**What goes wrong:**
You install the latest Ruby (3.3) locally, `bundle install` resolves to current gems, site builds fine locally. Push to Pages → build fails because GitHub Pages pins **Ruby 2.7 / 3.x** (varies — see pages-gem) and a fixed `github-pages` gem version. A gem that resolves locally to v5 may be pinned to v3 on Pages, causing Liquid/Sass syntax that works locally to error in CI.

**Why it happens:**
academicpages' `Gemfile` lists `gem "github-pages", group: :jekyll_plugins` — this *should* pin everything to match Pages. But forkers often run `bundle update` and lock to newer versions, or use `gem "jekyll"` directly.

**How to avoid:**
- Keep the `github-pages` meta-gem in `Gemfile`; do NOT replace with bare `jekyll`.
- Locally: `bundle exec jekyll serve` (never `jekyll serve` directly — bypasses Gemfile.lock).
- Cross-check against the dependency-versions page (`pages.github.com/versions/`) before adding any new gem.
- Commit `Gemfile.lock`.

**Warning signs:**
- Local build green, remote build red with `undefined method` or `wrong number of arguments` errors.
- `bundle exec jekyll --version` locally prints a version higher than pages.github.com/versions lists.

**Phase to address:** Skeleton

### Pitfall 6: Liquid template errors that only surface on Pages build (or render as literal text)

**What goes wrong:**
A `{% raw %}` block is forgotten around code samples that contain `{{ }}` — Jekyll tries to interpolate. A `{% include %}` references a partial that exists upstream but was deleted in the fork. A `{% for post in site.publications %}` works only because `_publications` is in `collections` in `_config.yml`; remove or rename and Liquid silently outputs nothing.

**Why it happens:**
Liquid errors in `--safe` mode (GitHub Pages) are often non-fatal — they render empty or as literal text rather than crashing the build, so the site "looks" deployed.

**How to avoid:**
- Always run `bundle exec jekyll build --strict_front_matter --strict_variables` locally before pushing. Treats undefined variables as build failures.
- Wrap any code example containing `{{` or `{%` in `{% raw %}...{% endraw %}`.
- Don't delete files under `_includes/` even if they look unused — a layout may include them conditionally.

**Warning signs:**
- A page renders with a section completely empty where you expected content.
- View-source shows literal `{{ page.title }}` text in the output.
- `_site/` differs between local and deployed.

**Phase to address:** Customisation (when editing layouts/includes)

### Pitfall 7: Image asset paths break after publishing

**What goes wrong:**
Markdown image `![photo](images/me.jpg)` works locally (relative resolution from page URL), 404s on Pages because the page lives at `/about/` and the image lives at `/images/me.jpg`. Or: image referenced as `/Harry-Rogers.github.io/images/me.jpg` (someone hard-coded the repo name during local testing on a project-page setup).

**Why it happens:**
academicpages convention is images in `/images/` at site root. Markdown editors resolve relative paths against the source file's directory, not the rendered URL.

**How to avoid:**
- Always use site-absolute paths: `![photo](/images/me.jpg)` (leading slash).
- Or use the `{{ site.baseurl }}/images/me.jpg` form inside Markdown that allows Liquid (most academicpages collections do).
- Lowercase all filenames (`me.jpg`, not `Me.JPG`) — Linux build is case-sensitive, macOS dev is not.
- Keep all images under `/images/` — don't scatter them next to Markdown files.

**Warning signs:**
- Photo missing on deployed site but visible in local preview.
- Browser dev tools network tab: image returns 404 with a Mac-cased filename (`Me.JPG` → `me.jpg`).

**Phase to address:** Content + Polish (link check)

### Pitfall 8: Dark-mode-only implementation leaks light styles

**What goes wrong:**
academicpages / Minimal Mistakes ships a light theme by default with Sass variables (`$background-color: #fff`, `$text-color: #3f3f3f`, etc.) and a `skins/` directory. Forkers attempt dark mode by:
1. Setting `minimal_mistakes_skin: "dark"` in `_config.yml` (good start, but does NOT cover the academicpages-specific overrides).
2. Adding a `prefers-color-scheme: dark` media query — fails for users on light-mode OS.
3. Adding a JS toggle UI but never wiring it up — clicks do nothing, looks broken.

Light bleed shows as: white flashes on page load, white backgrounds inside `<table>`, syntax-highlighting blocks with light backgrounds, `<code>` inline with light grey, social icons rendered in a dark colour invisible on dark background, syntax highlighter (`rouge`) using a light theme.

**Why it happens:**
The theme has ~6 Sass files with hardcoded light colours. `skin: dark` only swaps a subset. Code highlighting uses a separate Rouge theme entirely (not Sass-driven).

**How to avoid:**
1. Set `minimal_mistakes_skin: "dark"` in `_config.yml`.
2. Do NOT use `@media (prefers-color-scheme: dark)` — force dark unconditionally.
3. Create `assets/css/main.scss` with overrides that import the skin and then set:
   - `$background-color`, `$text-color`, `$border-color`, `$code-background-color`, `$primary-color`, `$link-color`, `$navicon-link-color-hover` — all dark-appropriate.
4. Replace the Rouge syntax-highlighting CSS (Minimal Mistakes uses `_syntax.scss`) — pick a dark Rouge theme like `base16.dark` or generate via `rougify style monokai > _sass/_syntax-dark.scss`.
5. Remove any theme-toggle UI from `_includes/masthead.html` and `_includes/footer.html` — academicpages doesn't ship one by default, but forkers sometimes add `<button>`s from blog posts.
6. Set `<meta name="color-scheme" content="dark">` in `_includes/head/custom.html` — prevents form controls and scrollbars rendering light on first paint.

**Warning signs:**
- White flash for ~200ms when navigating between pages (FOUC of light theme).
- Tables and code blocks have white backgrounds.
- iOS Safari address bar renders white (missing `<meta name="theme-color" content="#1a1a1a">`).
- Form inputs, `<select>`, scrollbars rendered in OS light style.

**Phase to address:** Customisation

### Pitfall 9: Sass overrides clobbered on upstream template upgrades

**What goes wrong:**
Forker edits `_sass/minimal-mistakes/_variables.scss` directly to change colours. Six months later runs `git merge upstream/master` to pull academicpages updates → merge conflicts in `_variables.scss`, or worse, no conflict but their overrides get reverted because they edited the wrong layer.

**Why it happens:**
Minimal Mistakes' layered Sass structure expects user overrides in `assets/css/main.scss` (top-level), NOT in `_sass/minimal-mistakes/*`. The vendored theme files are meant to be untouched.

**How to avoid:**
- All custom Sass goes in `assets/css/main.scss` BEFORE the `@import "minimal-mistakes"` line (for variable overrides) or after (for rule overrides).
- Never edit anything under `_sass/minimal-mistakes/`.
- Comment your overrides with `// CUSTOM: dark theme` so future-you can find them.
- Treat the fork as "downstream" — only customise via documented extension points.

**Warning signs:**
- Merge conflict from upstream pull in `_sass/minimal-mistakes/*.scss`.
- A theme change you made 3 months ago has silently reverted after a pull.

**Phase to address:** Customisation

### Pitfall 10: Email address scraped and spammed

**What goes wrong:**
Putting `Harry.Rogers@eng.ox.ac.uk` as plain text in `_config.yml` author block or in a Markdown page → harvested by bots within days → spam, phishing, conference scams ("Dear Dr. Rogers, we would like to invite you to publish in our journal...").

**Why it happens:**
academicpages' default `_config.yml` has an `email:` field that gets rendered as `<a href="mailto:...">` in author profile and footer. Plain-text mailto: in static HTML is the canonical spam-bot food.

**How to avoid:**
- Option A (safest): omit `email` from `_config.yml`; route contact through ORCID/LinkedIn/institutional page only.
- Option B (still useful, less protected): encode the address — e.g. write a small Liquid filter or use the academicpages convention of `email: "Harry.Rogers at eng dot ox dot ac dot uk"` rendered as text only.
- Option C: use Cloudflare email obfuscation, but that requires a custom domain — not in scope.
- For Harry: institutional email is *already* public on his Oxford page, so the marginal harm is small — but mailto: in HTML still increases volume measurably. Recommend Option B.

**Warning signs:**
- Within 1–2 weeks of going live, spike in spam to the academic address.
- View-source on deployed page shows literal `mailto:Harry.Rogers@...`.

**Phase to address:** Polish

### Pitfall 11: Missing/broken SEO and Open Graph metadata

**What goes wrong:**
- No favicon → tabs show generic globe.
- No OG tags → LinkedIn/Twitter share shows blank card or page raw text.
- `jekyll-seo-tag` not configured → `<title>` is just "Home" on every page.
- No `og:image` → no preview image in shares.
- Robots.txt missing or accidentally `Disallow: /` (copy-pasted from a staging template).
- Sitemap pointed at `academicpages.github.io` (see Pitfall 2).

**Why it happens:**
academicpages bundles `jekyll-seo-tag` and `jekyll-sitemap` but they need correct `_config.yml` values to be useful. Default fork values point at upstream.

**How to avoid:**
- Set `_config.yml`: `title`, `description`, `author.name`, `author.bio`, `author.avatar`, `og_image: /images/og-card.png` (1200×630 px).
- Add `<link rel="icon" type="image/png" href="/images/favicon.png">` and `<meta name="theme-color" content="#1a1a1a">` to `_includes/head/custom.html`.
- Verify with: opengraph.xyz, cards-dev.twitter.com/validator, linkedin.com/post-inspector.
- Submit `https://harry-rogers.github.io/sitemap.xml` to Google Search Console.
- Per-page front matter: `title:`, `excerpt:`, `header.og_image:`.

**Warning signs:**
- Sharing the URL on LinkedIn/Twitter shows no preview card or shows the academicpages owner's photo.
- Google "site:harry-rogers.github.io" after a week returns no results or returns academicpages content.

**Phase to address:** Polish

### Pitfall 12: BibTeX / publications data quality

**What goes wrong:**
- BibTeX keys with special characters break Jekyll's Markdown parser (`@` in `@inproceedings{rogers@2023}`).
- Author list copy-pasted from Google Scholar in wrong order (Scholar sorts alphabetically for some views).
- Year mismatched between front matter (`date: 2023-06-15`) and citation (`2024`).
- Missing publisher / venue strings render as `undefined` or empty.
- PDF link points to `arxiv.org/abs/2401.12345v1` instead of stable `/abs/2401.12345` (v-suffix can rot).
- Hyphenated or accented author names (`De La Iglesia`, `Schölkopf`) escaped wrong → "De La Iglesia" becomes "De\xa0La Iglesia" or "De La\\\\xa0Iglesia".
- Conference acronyms vs full names inconsistent (TAROS vs "Towards Autonomous Robotic Systems").
- DOI missing — peers cannot verify; reduces credibility.

**Why it happens:**
academic publication metadata is fiddly; copy-paste from BibTeX export of conference sites often has stray braces, non-ASCII characters, line breaks.

**How to avoid:**
- One file per publication in `_publications/`, named `YYYY-MM-DD-short-slug.md`.
- Front matter template MUST include: `title`, `collection: publications`, `permalink`, `excerpt`, `date`, `venue`, `paperurl` (DOI URL preferred over arxiv/PDF), `citation` (string), `bibtex` (raw block).
- Validate BibTeX in a parser (e.g. `bibtex-tidy` CLI) before committing.
- Author list ordering: match the published version, not Scholar's view. Bold Harry's name in the citation string.
- Use DOI permalinks (`https://doi.org/10.1109/...`) — they don't rot.
- Cross-check every entry against ORCID and Google Scholar before going live.

**Warning signs:**
- A publication's citation displays `Rogers, H. and undefined and undefined`.
- Special characters render as `?` or `Ã©`.
- Click "paper" → 404 or paywall page with no preprint fallback.

**Phase to address:** Content

### Pitfall 13: "Under construction" placeholders and demo content left in production

**What goes wrong:**
academicpages ships with rich demo content: fake publications by "John Doe", a sample blog post about "Welcome to Jekyll", placeholder talk slides, a fake portfolio item, a sample teaching page about "Teaching Experience 1". Forkers ship without removing these. Recruiters Google "Harry Rogers Oxford" → land on a page mixing real publications with "Paper Title Number 1" / "This paper is about a person who is..." → credibility destroyed.

**Why it happens:**
Excitement to deploy beats the boredom of deleting placeholders. Some placeholders live in `_data/`, `_pages/`, `_publications/`, `_talks/`, `_teaching/`, `_portfolio/` — easy to miss.

**How to avoid:**
Before flipping `_config.yml: published: true` (or before announcing the URL):
- `find . -path ./node_modules -prune -o -type f \( -name "*.md" -o -name "*.html" \) -print | xargs grep -l -i -E "(lorem ipsum|john doe|paper title number|teaching experience [0-9]|talk [0-9]|under construction|coming soon|placeholder)"` — must return zero results.
- Delete every file in `_publications/`, `_talks/`, `_teaching/`, `_portfolio/` from the fork and replace with real content (or leave empty if no entries).
- Delete `_posts/` entirely (no blog per project scope).
- Replace `images/profile.png` with Harry's actual photo.
- Replace `_pages/about.md` upstream content.

**Warning signs:**
- Site has a publication titled "Paper Title Number 1".
- News/blog shows a Jekyll welcome post.
- Profile photo is a silhouette or someone else's face.
- Any page contains "Lorem ipsum".

**Phase to address:** Content (gating before site is shared)

### Pitfall 14: Stale affiliations and outdated facts

**What goes wrong:**
Site says "PhD student at UEA" two years after graduation; lists Syngenta collaboration but not Oxford role; "Currently looking for postdoc positions" left in the bio after starting at Oxford. Especially insidious because *the site looks finished* — there's no visible bug, just out-of-date facts that erode trust.

**Why it happens:**
Initial content drafted from CV at a point in time. Site is not part of a regular review cadence. Author moves on, doesn't update.

**How to avoid:**
- Single source of truth for current role: a `_data/author.yml` (academicpages uses `author:` in `_config.yml`) — update there, propagates everywhere.
- Add a `last_updated: 2026-05-17` line in the footer (Liquid: `{{ site.time | date: "%B %Y" }}` auto-updates on each build).
- News section forces recency — if the most recent news entry is >6 months old, that's a visible signal to refresh.
- Calendar reminder every 6 months to audit landing page against ORCID + Oxford people page.

**Warning signs:**
- Most recent news entry > 12 months old.
- Bio still uses present tense for a past role.
- Email address is `@uea.ac.uk` (expired) but site is otherwise current.

**Phase to address:** Content + ongoing (post-launch)

### Pitfall 15: Mobile layout broken because academicpages sidebar is fixed-width

**What goes wrong:**
academicpages uses a fixed-width left sidebar with author info. On narrow viewports it collapses to top-of-page, but custom additions (long affiliation string, multiple social icons, manually-added div) can blow out the layout — horizontal scrollbar appears, text overflows screen, content gets pushed below the fold on mobile.

**Why it happens:**
Forkers add content to the sidebar (`_config.yml` author block, `_includes/author-profile-custom-links.html`) without testing at 375px width.

**How to avoid:**
- Test in Chrome DevTools at iPhone SE width (375×667) at every customisation commit.
- Keep sidebar entries short (max ~30 chars per line).
- Run Lighthouse mobile audit (target 90+) before declaring done.
- Use `min-width: 0` on any custom flex children to prevent overflow.

**Warning signs:**
- Horizontal scroll on phone.
- Pinch-zoom needed to read body text.
- Lighthouse mobile score < 80.

**Phase to address:** Customisation + Polish

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|---|---|---|---|
| Hard-code publication HTML directly in a single `publications.md` page instead of `_publications/` collection | Skip learning Jekyll collections | Every new paper requires hand-edits to one giant file; no auto-sort by date; no per-paper permalink for sharing | Never — collection is already wired in the template, cost is one-time |
| Edit `_sass/minimal-mistakes/*.scss` directly for dark mode | Quick visual result | Upstream merges conflict; no clean upgrade path | Never — use `assets/css/main.scss` |
| Skip `Gemfile.lock` commit, "Pages handles versions anyway" | Cleaner diffs | Local builds drift from Pages, breakage hard to reproduce | Never |
| Leave `jekyll new`-style `_posts/welcome-to-jekyll.md` in place | One less file to delete | Credibility hit, mixes a blog post into a no-blog site | Never (post-launch) |
| Use Google Scholar HTML scrape rather than maintaining `_publications/` | Lower content maintenance | Scholar HTML is unstable, blocks bots, layout is ugly, no BibTeX | Only if author has 100+ papers — not Harry's case |
| Keep light-mode CSS "just in case I want a toggle later" | Optionality | Bundle size, FOUC risk, never actually used | Never given the explicit dark-only decision |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|---|---|---|
| GitHub Pages build | Adding a non-allowlisted plugin and assuming it'll work | Check pages.github.com/versions/; if not listed, either drop the plugin or move to a GH Actions Jekyll build workflow |
| Google Scholar | Linking via the long URL with `user=` parameter and trusting it's permanent | Scholar URLs are stable by `user=` ID — Harry's `sPwcwvMAAAAJ` is fine; do NOT link by name search |
| ORCID | Embedding the ORCID iD as text only | Use the official ORCID iD HTML snippet (logo + verified link to https://orcid.org/0000-0003-3227-5677) per ORCID's brand guidelines |
| LinkedIn | Linking to `/in/harry-rogers` (a name slug) | Slug works but can change if user edits it; if profile URL is stable, fine — verify before launch |
| arXiv | Linking with version suffix (`v1`, `v2`) | Use the bare DOI / unversioned arXiv ID — `arxiv.org/abs/2401.12345` not `…v2` |
| DOI | Linking to publisher site (e.g. `ieeexplore.ieee.org/document/12345`) | Use `https://doi.org/...` — survives publisher migrations |
| Google Analytics | Adding `analytics.google.com` tracking ID without a privacy policy | Either omit analytics entirely (recommended for an academic site, GDPR-clean) or add a privacy page |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|---|---|---|---|
| Large hero/profile image (5+ MB) | Slow LCP, mobile data warning | Resize to ≤500 KB, prefer WebP, use `<img loading="lazy">` for non-hero images | First page load on 3G; any time |
| Unoptimised publication thumbnails | News/papers page slow | Constrain to 600px wide, JPEG q85 or WebP | At ~10+ publications |
| Linking to PDFs hosted on slow institutional servers | Click → 5+ second wait | Mirror PDFs to `/files/` in the repo (≤100 MB total repo size) or use the publisher DOI which redirects | Always |
| Jekyll site with `paginate: 5` on a list with thousands of entries | Build time grows | Not applicable at Harry's scale (~10 publications) | At 500+ entries |

## Security Mistakes

| Mistake | Risk | Prevention |
|---|---|---|
| Email in plaintext mailto: | Spam, phishing | See Pitfall 10 |
| Personal phone number on the site | Harassment, doxxing | Omit entirely; institutional contact only |
| Home address or personal location | Stalking | Omit; "Oxford, UK" max |
| Committing draft/unpublished paper PDFs to `/files/` | Embargo break, copyright issue with publishers | Keep `/files/` to author-accepted manuscripts only; check publisher self-archiving policy (SHERPA/RoMEO) per paper |
| Photos of students / collaborators without consent | Privacy/data-protection (GDPR for UK/EU subjects) | Use only photos where consent is documented; for teaching outreach photos, blur faces or use wide shots |
| GitHub repo set to private after going live | Pages stops serving (public repo required on free tier) | Keep repo public; if there are private notes, put them in a separate repo or `.gitignore` |
| Leaving `_config.yml` `repository:` pointing at a forked org's repo containing PRs | Confusing PR/issue cross-references | Set `repository: Harry-Rogers/Harry-Rogers.github.io` explicitly |

| Generic stock photo of "scientist in lab coat" as hero | Looks like a template, not a person | Real photo of Harry, neutral background, recognisable |

| "Click here" link text | Accessibility/SEO failure | Descriptive link text: "Read on arXiv", "View DOI" |

| CV link present but 404 | "This site is broken" impression | Either include the CV PDF, or remove the link entirely until Phase 2 (explicit project decision already says: defer, do not include broken link) |
| Page titled "Untitled" or "Page 1" | Looks unfinished | Every page has a meaningful `title` in front matter |

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---|---|---|
| Wrong repo name (Pitfall 1) | LOW | Settings → rename repo → wait 1–2 min → re-check URL |
| Wrong baseurl (Pitfall 2) | LOW | Edit `_config.yml`, commit, wait for rebuild |
| Plugin failure (Pitfall 4) | MEDIUM | Remove plugin from Gemfile + `_config.yml`, or migrate to GH Actions build |
| Ruby drift (Pitfall 5) | LOW | Pin to `github-pages` gem, `bundle install`, commit Gemfile.lock |
| Sass overrides clobbered (Pitfall 9) | MEDIUM | Recover overrides from git history, move to `assets/css/main.scss` |
| Email harvested (Pitfall 10) | HIGH (cannot un-leak) | Switch to obfuscated form; consider new alias if spam intolerable; institutional spam filter |
| Placeholder content leaked (Pitfall 13) | LOW technically, HIGH credibility | Remove immediately; site is small enough that recovery takes minutes; rely on initial pre-launch grep |
| Broken publication metadata (Pitfall 12) | LOW per entry | Fix one Markdown file at a time, Pages rebuilds on each push |
| Mobile broken (Pitfall 15) | LOW | Add CSS media-query override in `assets/css/main.scss`; do not edit theme files |
